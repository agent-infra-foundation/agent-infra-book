# 第 0 部分 — 智能体沙箱实践概览

[English](PART-0.md) | **简体中文**

*围绕智能体运行时中的隔离、状态、rollout、恢复与发布展开的对比案例研究。*

“智能体沙箱”听起来像一个单一类别。实践中，这个标签涵盖命令策略、私有工作空间、
容器、微型虚拟机（microVM）、浏览器会话、rollout 环境、检查点和集群控制。本部分
以一次依赖更新为贯穿案例，沿着这些边界说明每一层保护什么、保留什么，又返回什么。

这些区分使运维者能够比较不同系统，而不必假定速度、隔离、恢复和发布必然由同一产品
以不可分割的方式一并提供。

## 第 0 章 — 智能体工作负载与运行时底座

### 那台曾经只服务于一个人的计算机

一名开发者让三个编码智能体更新同一个依赖。它们编辑同一份检出，生成彼此冲突的锁定
文件，还在同一个端口启动测试服务器。每个智能体都在报告进度，却没有人说得清最终
状态归谁所有。

操作系统其实运转正常：一个用户可以启动进程、修改文件。消失的是那种分配所有权、
决定保留哪些结果的人类协调机制。在智能体规模下，每次尝试都需要私有执行、稳定身份、
受限资源、具名起始状态、历史记录，以及受控的返回路径。

**沙箱环境**容纳一次执行的工具、进程、浏览器状态和工作空间。**智能体运行时**调用
模型、选择动作并吸收观测结果。两者相互协作，却不是同一个组件。

> *💡 **核心原则：** 沙箱环境承载执行状态；智能体运行时拥有决策循环。*

![个人计算机演变为受管理的智能体工作空间群体](../assets/illustrations/part-0/00-human-to-agent-runtime.png)

*图 0.1 — 一个人可以非正式地协调个人计算机；一群智能体则需要明确的私有工作、控制与
返回路径。*

### 恰好两种部署位置模式

第一个架构问题是智能体运行时在哪里运行。只需做一个测试：

> *🧭 **位置测试：** 模型 → 工具 → 观测 → 下一次模型调用，这个循环在哪里运行？*

**答案恰好只有两个。**

对于**沙箱内智能体**，智能体运行时与其工具、进程和工作空间一起运行在沙箱环境内。
调用远程模型服务不会改变这一分类。解释模型响应、选择工具、接收结果并准备下一次模型
调用的组件仍然位于沙箱内部。

对于**采用沙箱化工具执行的外部智能体**，智能体运行时位于沙箱环境之外。它通过执行
协议发送操作：请求、任何流式输入或输出，以及结果。沙箱内的执行工作进程负责完成这些
操作。它可以持有 PTY、暴露 MCP 服务器或管理进程，但它不拥有决策循环，因此不是另一
个智能体运行时。

![仅有的两种智能体部署位置模式](../assets/diagrams/part-0/00-agent-placement-modes.svg)

*图 0.2 — 部署位置只取决于决策循环在哪里运行；远程模型服务和沙箱侧工作进程都不会
产生第三种模式。*

| 维度 | 沙箱内智能体 | 采用沙箱化工具执行的外部智能体 |
| --- | --- | --- |
| 智能体运行时 | 位于沙箱环境内 | 位于沙箱环境外 |
| 工具路径 | 本地调用和系统接口 | 通过执行协议连接执行工作进程 |
| 私有状态 | 除非导出，否则通常与环境耦合 | 工作空间和进程留在内部；会话历史可以留在外部 |
| 故障形态 | 运行时和环境可能一起失效 | 运行时可以替换环境或重新连接环境 |
| 主要成本 | 镜像更大、生命周期耦合 | 传输、序列化和远程工具语义 |
| 关键不保证项 | 本地性不代表强隔离 | 外部编排不代表状态持久或可发布 |

两种部署方式都不会永远胜出。沙箱内运行时可以自然使用本地 CLI、PTY、套接字和文件，
但其生命周期与凭证可能和环境耦合。外部运行时可以保留历史、替换环境，并让凭证远离
生成代码的执行过程；但其协议必须表达流式传输、stdin、PTY 尺寸调整、长时进程、端口、
制品、断开连接和幂等重试。

在这条协议边界上，“完成”还必须定义输出何时已经刷新、进程何时退出、制品何时捕获，
以及工作空间变更何时可见。操作标识可以避免因响应丢失而重复发布软件包或执行迁移。
这些是外部边界带来的分布式系统义务，而不是第三种部署位置模式。

沙箱即服务（Sandbox-as-a-Service）是一种交付模式，不是第三种部署位置模式。
Anthropic 的 Managed Agents 架构展示了外部模式：外部执行框架拥有决策循环和持久日志，
可替换的执行工作进程则充当它的“双手”。[Anthropic 工程说明](https://www.anthropic.com/engineering/managed-agents)

### 私有房间不等于运行时

给每个智能体一个私有目录后，最明显的文件冲突消失了，但更难的问题仍在。智能体能否
读取用户的 SSH 密钥？两个测试服务器能否绑定同一端口？内存耗尽时会怎样？哪个基础
版本产生了这个结果？失败的尝试能否恢复？下载的制品是否属于共享历史？谁来授权发布？

这些问题揭示出六种压力。

**并发**要求明确文件、进程、端口及其他可变状态的所有权。**可审计性**要求把身份和
起始状态与工具事件及输出关联起来。**成本**要求快速创建、高密度部署、暂停和清理，而
不是为每个短任务准备一台永久机器。**可复现性**要求显式模板和基础版本。**恢复与探索**
要求快照、分叉或重放。**发布**要求通过决策把私有结果转化为共享事实。

一份看似合理的文件加一句“测试已通过”远远不够。信任需要结构化因果链：智能体与会话、
起始版本、策略、命令、进程、制品，以及提议修改的精确字节。有了这份记录，恢复才能区分
从基础版本重跑、从保留的工作空间状态继续，以及重新连接仍在运行的进程。

Git、Shell 历史和 CI 各自保存了这段故事的碎片。会话历史必须把它们连接起来，免得人类
手工重建执行过程。它应记录具名状态转换：测试后环境丢失、从保留工作空间替换运行时，
或传输失败后重新连接。这样，恢复才是从明确状态继续，而不是发出语义含糊的重试。

安全贯穿上述六点，但把智能体沙箱定义为“容纳恶意代码”仍然过窄。一个系统可以在客户机
内核和宿主机之间提供强隔离，却不给出可用的变更集。另一个系统可能面向协作型智能体，
能提供出色的工作空间溯源，却不声称实现恶意租户隔离。提到“沙箱”时，必须同时说明其
单元、边界、状态模型和返回路径。

![最低限度的智能体运行时底座](../assets/diagrams/part-0/00-agent-runtime-reference.svg)

*图 0.3 — 只有当策略和会话历史围绕着一条从动作到返回或发布的受控路径时，私有执行
才值得信赖。*

最低限度的底座包括：智能体运行时通过沙箱环境操作私有工具与工作空间，外部由策略和
会话历史包围，并具有明确的返回或发布路径。控制器、调度器、检查点存储和凭证代理则在
规模化场景中进一步完善这条路径。

评估任何系统时，都应明确其单元、部署位置、边界、私有状态与基础版本、生命周期、并发
模型、证据、返回路径，以及最重要的不保证事项。这样可以避免拿文件系统和虚拟机相比，
或把功能列表当成架构：名称相似的快照、工作树和沙箱，覆盖的状态与信任边界可能完全不同。

接下来各章会让同一个任务——更新依赖、修改源文件、运行测试、打开应用并返回提案——
穿过这片技术版图的不同区域。每个类别解决的都是不同问题；任何一个都不应被误认为完整的
智能体计算机。

## 第 1 章 — 编码智能体产品中的沙箱

### 规则、工作空间与执行边界

假设现在让这次依赖更新分别在三个 Git 工作树中运行。智能体不再相互覆盖文件，但三者
仍可能看到同一个主目录、同一组凭证、同一个内核、同一张网络和同一批本地服务。工作树
是一张私有书桌，不是一间上锁的房间。

编码智能体产品会组合几种容易混淆的边界：

- 权限策略规定哪些操作无需批准即可执行。
- 私有工作空间隔离尚未完成的文件编辑。
- 进程沙箱限制文件系统、进程或网络访问。
- 容器对资源进行命名空间隔离，但通常仍共享宿主机内核。
- VM 或 microVM 增加客户机内核边界。

**这些控制机制可以组合，却不能排成一条通用的强度刻度。** 对协作式编码而言，工作树
可能恰好解决最重要的冲突；当执行的代码不可信时，则可能必须使用 microVM。反过来，
microVM 本身也没有说明如何比较或合并两个优秀补丁。

> *🧱 **边界规则：** 先问被隔离的是文件、进程、网络、内核还是策略，再问还有什么保持共享。*

![不同隔离机制回答不同问题](../assets/diagrams/part-0/01-isolation-boundaries.svg)

*图 1.1 — 从策略走向客户机内核改变了哪些资源仍然共享；它不会自动增加历史记录或发布能力。*

Codex 展示了这些概念的分离。在本地对话中，派生出的命令运行在平台原生沙箱内，而
智能体运行时仍位于这条命令边界之外，因此属于采用沙箱化工具执行的外部智能体。批准
机制决定 Codex 何时必须先询问再越过边界；沙箱则强制限定命令在边界内可以做什么。
Codex 工作树提供共享 Git 元数据的独立工作副本。它们减少编辑冲突，但并未被描述为租户
安全边界。云端对话则会创建容器、检出选定版本、运行环境设置、执行任务，并返回答复和
差异。[Codex 沙箱文档](https://learn.chatgpt.com/docs/sandboxing)、
[工作树文档](https://learn.chatgpt.com/docs/environments/git-worktrees)、
[云端环境文档](https://learn.chatgpt.com/docs/environments/cloud-environment)

Claude Code 在本地也做了类似区分。它的 Bash 沙箱对命令及其子进程施加文件系统和网络
限制，并由操作系统原语执行这些边界。Claude Code 智能体运行时仍在 Bash 命令边界之外，
所以这同样是采用沙箱化工具执行的外部智能体。文档明确将权限规则与沙箱强制机制分开，
并说明无法在沙箱内运行的命令应如何受控地回退。[Claude Code 沙箱文档](https://code.claude.com/docs/en/sandboxing)

Docker Sandboxes 展示了另一种部署位置模式。Docker 在隔离的 microVM 内启动编码智能体，
其中具有独立的 Docker 守护进程、文件系统和网络。智能体运行时、工具和工作空间都位于
该沙箱环境中；模型服务仍可远程运行。这属于沙箱内智能体。与工作树相比，microVM 提供
更强的宿主机边界，但文档并未把它描述成发布系统。[Docker Sandboxes 文档](https://docs.docker.com/ai/sandboxes/)

| 示例 | 单元与部署位置 | 边界与私有状态 | 生命周期、证据与返回 | 关键不保证项 |
| --- | --- | --- | --- | --- |
| Codex 本地 | 命令执行；外部智能体 | 操作系统强制的命令沙箱；可选工作树 | 对话历史和差异；工作树可以移交或恢复 | 工作树不是客户机内核边界 |
| Claude Code 本地 | Bash 执行；外部智能体 | 操作系统强制的文件系统和网络限制 | 会话及工作目录变更；例外遵循权限流程 | 权限批准不等于隔离 |
| Docker Sandboxes | microVM；沙箱内智能体 | 客户机内核、私有 Docker 守护进程、文件系统和网络 | 环境在沙箱会话期间持续存在；成果通过 Git 或导出文件带出 | microVM 隔离无法裁决互相竞争的变更 |

这个任务揭示了三者的区别：工作树回答“文件属于谁”，命令沙箱回答“允许哪些操作”，
microVM 则限制宿主机暴露面。它们都不会决定结果应以提交、补丁还是制品的形式返回。

这些例子也说明了并发问题。十个私有工作树可以阻止十个智能体互相覆盖源文件，但它们
仍在争用宿主机的 CPU、内存、磁盘、端口和受速率限制的外部服务。十个 microVM 可以
隔离更多资源，却需要更高的启动与运营成本。优秀的编码智能体产品会明确自己防止哪一种
冲突，而不是把“已沙箱化”当作分析终点。

Gemini CLI 记录在案的选择进一步强化了这种分类观：它可以使用挂载工作空间的容器、
gVisor，或工具级沙箱。决定边界的不是产品名称，而是选中的机制。
[Gemini CLI 沙箱文档](https://geminicli.com/docs/cli/sandbox/)

评估任何编码智能体沙箱时，应先问哪些东西会穿过边界：工作空间、共享 Git 元数据、凭证、
网络流量、缓存、Docker 套接字、本地服务，以及显式批准的越界操作。然后再问什么会返回。
终端记录和修改后的文件或许足够服务一位开发者，但并行智能体需要更审慎的返回契约。

## 第 2 章 — 按需云沙箱

### 一台拥有生命周期 API 的计算机

同一个任务现在以这样的请求到达某项服务：“给这个智能体一台干净的 Linux 计算机，使用
二十分钟。”请求听起来很简单，直到测试已经通过、补丁尚未下载，运行却超时了。机器得到
了隔离，工作成果仍然丢失。

理解按需云沙箱的最佳方式，是把它看作一台具有显式生命周期的计算机。模板定义起始工具
和依赖。分配操作创建身份和私有状态。活跃执行拥有进程、文件和端口。暂停或快照可以保留
部分状态；超时或销毁操作则终止其余状态。最后，返回路径把选定的值、文件、制品、URL、
快照或补丁带到另一个系统。

> *🔄 **生命周期规则：** 隔离保护运行中的沙箱；保留和返回保护它产生的工作成果。*

“全新”可能指一个新进程、干净文件系统、缓存模板、已恢复的快照，或续用的机器。这些
状态在运维上并不相同。**可复现性取决于为基础版本命名**，而不只是把结果称为全新。

![生命周期选择决定私有工作能否留存](../assets/diagrams/part-0/02-sandbox-lifecycle.svg)

*图 2.1 — 停止、暂停、导出和销毁是不同的状态转换，因为它们保留的状态不同。*

E2B 通过 SDK 暴露按需 Linux VM 和模板。其文档分别说明生命周期、持久化、快照、分叉、
文件系统传输、命令、指标和遥测。在常见 API 拓扑中，外部智能体运行时请求 VM 执行工具，
因此属于采用沙箱化工具执行的外部智能体。调用者也可以把智能体运行时安装进模板，从而
采用沙箱内模式；交付服务本身并不决定部署位置。[E2B 文档](https://e2b.dev/docs)

Daytona 同样通过 SDK 和 API 提供沙箱，并记录了暂停与快照操作。其文档区分仅包含文件
系统的冷快照，和包含内存的实验性快照。这个细节很重要：恢复文件并不等于恢复运行中的
进程。这些是厂商文档所述的能力，不是独立性能基准。[Daytona 沙箱文档](https://www.daytona.io/docs/en/sandboxes/)

Modal Sandboxes 以另一种方式让生命周期边界清晰可见：文档建议，当工作必须超出沙箱的
最长运行时间时使用文件系统快照。因此，一个长期项目是由连续创建的环境和保留文件组装
起来的，而不是默认依赖一台永生机器。[Modal Sandbox 文档](https://modal.com/docs/guide/sandboxes)

| 示例 | 单元与部署位置 | 隔离与私有状态 | 生命周期、并发与审计 | 返回与不保证事项 |
| --- | --- | --- | --- | --- |
| E2B | 按需 VM；通常为外部智能体 | VM 文件、进程和环境 | 创建、连接、暂停、快照、分叉；文档记录指标与遥测 | 文件、命令结果、URL、快照；没有内置合并契约 |
| Daytona | 从镜像或快照创建的沙箱；通常为外部智能体 | 私有文件系统和实验性进程内存快照 | 创建、暂停、恢复、快照；多个沙箱由 API 管理 | 文件和命令结果；快照不等于发布 |
| Modal | 沙箱进程环境；常见 API 用法为外部智能体 | 文件系统，以及挂载的卷或快照 | 有限运行时长，可选择保留文件系统 | 函数结果和文件；生命周期上限依然存在 |

生命周期动词需要精确定义。“暂停”可能冻结进程，也可能只保留文件；预览 URL、计费状态
和可重连身份可以遵循不同规则。返回同样需要具体说明：stdout 会遗漏编辑，选定文件可能
遗漏删除，快照可能保留秘密，而补丁则假设存在一个基础版本。稳健的工作流会把诊断性保留
与可审查提案分开，只有在输出和历史完成关联后才销毁环境。

共同的不保证事项具有决定性：**任务沙箱通常返回材料，而非共享事实。** stdout 可以说
测试已通过，有用的补丁却仍留在内部。文件下载可能漏掉删除操作。快照可能保留过多状态，
不适合审查。分支也可能与更新后的基础版本冲突。调用方仍然需要捕获、比较和发布。

## 第 3 章 — 浏览器与计算机操作沙箱

### 像素背后的状态

依赖更新通过测试后，智能体打开应用并登录测试环境账户。它关闭横幅、更改偏好设置、下载
报告，然后把控制权交给人类确认付款。关闭浏览器进程并不能回答这次交互的哪些部分应该
持久保留。

浏览器沙箱承载的不只是可执行代码。标签页、Cookie、localStorage、IndexedDB、下载项、
浏览器权限、身份验证、显示状态和输入状态都可能影响下一步动作。一次性的浏览器会话可以
挂接持久配置档案。人类实时查看或接管也会进入同一状态。即使会话本身消失，截图、录像、
提取数据和下载文件仍可离开沙箱。

> *🔐 **状态规则：** 浏览器进程可以是一次性的，而已认证配置档案、证据和下载内容可以持久保留。*

![浏览器状态拥有多种生命周期和返回路径](../assets/diagrams/part-0/03-browser-session-state.svg)

*图 3.1 — 浏览器进程可以是临时的，而身份、证据和选定输出分别遵循不同的保留规则。*

Browserbase 明确区分了配置档案。默认情况下，会话从一个全新的用户数据目录开始；
Context 可以跨会话保留 Cookie、身份验证令牌、本地存储、IndexedDB 及其他应用数据。
若希望会话中的修改更新该 Context，必须启用持久化。在通常拓扑中，外部智能体运行时
通过自动化协议驱动远程浏览器，所以它属于采用沙箱化工具执行的外部智能体。
[Browserbase Context 文档](https://docs.browserbase.com/platform/browser/core-features/contexts)

AIO Sandbox 展示了另一种单元：一个 Docker 容器通过共享文件系统组合浏览器自动化、
VNC、Shell、文件、Notebook、编辑器和 MCP 界面。外部智能体客户端可以把这些界面当作
工具调用。这种集成很方便，因为下载文件会立即出现在 Shell 中；但共享容器本身既不会
形成更强的租户边界，也不会创建发布事务。[AIO Sandbox 仓库](https://github.com/agent-infra/sandbox)

| 示例 | 单元与部署位置 | 私有状态与生命周期 | 可审计性与返回 | 关键不保证项 |
| --- | --- | --- | --- | --- |
| Browserbase | 远程浏览器会话；外部智能体 | 全新会话数据或保留的 Context | Context 身份及浏览器自动化结果 | 保留登录状态是敏感状态，不是授权证明 |
| AIO Sandbox | 工具丰富的容器；其客户端拓扑采用外部智能体 | 浏览器、显示、工具和工作空间共享同一容器 | 工具结果、文件、截图和远程视图 | 单个容器不代表恶意租户隔离或代码发布 |

一次会话可以产生报告、截图、浏览器事件、源代码编辑、人类决策和更新后的配置档案。它们
需要不同的返回与保留规则：制品离开沙箱，证据保持可归因，代码转化为变更集，认证状态
则持续绑定到其所有者和策略。

拆除环境时必须平衡机密性与可复现性。保留的配置档案既可能保存所需登录，也可能保留已
遭入侵的会话；删除所有配置档案则可能迫使系统反复处理凭证。因此，系统需要所有者、
保留规则、撤销路径和事件历史。

可视化界面还带来另一个陷阱：**截图只是观测，不是状态本身。** 两个页面可以外观完全
相同，Cookie、权限、下载内容和开放连接却不一样。因此，可靠的计算机操作评估与重放，
需要在像素之外同时记录结构化浏览器与会话事实。

配置档案和截图可能保留权限或秘密，因此浏览器基础设施必须绑定身份、脱敏、证据和配置
档案生命周期。人类接管必须明确标记，观测结果也不得被误认为已获批准的项目变更。

## 第 4 章 — RL 与评估沙箱

### 将一个状态分叉成一组 rollout

重复尝试应该共享一个已经初始化的根状态，然后在模型决策处分化，而不必重新构建操作系统
和缓存。在蒙特卡洛树搜索（MCTS）中，控制器选择并恢复节点、扩展动作、让私有分支继续
rollout（轨迹展开）、为叶节点评分，再反向传播奖励和访问次数。

RL 与评估为执行增加了一个**回合契约**。数据集条目指定任务和初始状态；智能体产生动作；
环境返回观测并改变私有状态；验证器给出奖励；类型化终止则关闭这次尝试。回合记录把结果
与确切策略、轨迹、验证器和起始检查点关联起来。

> *🌲 **Rollout 规则：** 从一个具名根状态启动，分叉私有分支，为叶节点评分，并记录每项奖励所对应的确切检查点。*

![MCTS 将已启动的沙箱状态分叉为并行私有 rollout](../assets/diagrams/part-0/04-rl-environment-stack.svg)

*图 4.1 — 外部 MCTS 控制器启动一个干净检查点，恢复选定状态，分叉出私有沙箱进行并行
rollout，评估叶节点并反向传播分数。CubeSandbox 或 DeltaBox 可以加速状态复用；两者都
不提供搜索策略或验证器。*

图中把选中的节点物化为检查点，但具体实现可以只保存分支点、重放成本较低的节点，或淘汰
旧状态。每次 rollout 仍必须从其选中节点所指明的状态开始。

CubeSandbox 的文档说明了 RustVMM/KVM microVM、兼容 E2B 的 API、集群部署，以及对运行中
沙箱执行检查点、克隆和回滚的操作。因此，外部控制器可以启动模板、扇出隔离分支，并保留
选定检查点。这些是项目文档所述的能力，并不构成数据集、搜索策略、奖励或训练器。
[CubeSandbox 仓库](https://github.com/TencentCloud/CubeSandbox)和
[生命周期文档](https://cubesandbox.com/guide/lifecycle.html)

DeltaBox 协调文件系统变更与进程状态，以实现基于变更的检查点与回滚。其作者报告了在
SWE-bench 树搜索和 RL 扇出实验中的毫秒级延迟；这些研究结果既不是服务保证，也不是完整
训练栈。[DeltaBox 论文](https://arxiv.org/abs/2605.22781)和
[项目页面](https://dongyunpeng-sjtu.github.io/deltabox/)

| 沙箱底座 | 单元与部署位置 | 分叉与回滚状态 | 并行 rollout 角色 | 返回与不保证事项 |
| --- | --- | --- | --- | --- |
| CubeSandbox | KVM microVM 沙箱；通常采用沙箱化工具执行的外部智能体 | 模板，以及对运行状态执行快照、克隆和回滚的操作 | 控制器可以在服务或集群上扇出私有 microVM 分支 | 返回执行与沙箱状态；不定义 MCTS、奖励或训练 |
| DeltaBox | 由外部搜索或训练循环控制的有状态智能体沙箱 | 利用变更状态协调文件系统与进程的检查点/回滚 | 减少树搜索与 RL 扇出期间重复物化状态的成本 | 恢复智能体状态；不定义验证器、搜索策略或集群服务 |

图中的控制器属于采用沙箱化工具执行的外部智能体。沙箱内智能体仍然可行，但控制器依旧
必须分配回合身份、收集分数并选择节点。

重置语义决定奖励能否正确归因。重新构建简单却昂贵；恢复快照只有在覆盖所有相关状态域时
才会更快。文件回滚不会停止残留进程，也无法撤销远程数据库写入。因此，回合记录必须明确
重置机制、检查点和未被捕获的外部影响。

根状态必须指明镜像、仓库版本、初始化过程、策略和保留的进程状态。每个子节点随后独占其
文件、进程、轨迹、终止状态和奖励，同时引用共享前缀。否则，缓存、服务器或数据库行可能
在分支之间泄漏工作，从而污染奖励。

失败分支可以销毁，潜力较高的叶节点则可成为下一个检查点。这样的提升会改变保留状态；
它不得把未完成的子节点状态合并进兄弟节点。分叉谱系让共享历史保持不可变，同时把每项
奖励附着到其 rollout 分化的位置。

基础设施故障不是智能体失败。分配、恢复、协议、验证器、策略和模型终止都需要类型化结果
和重试规则。每项奖励必须引用确切的检查点、模型、运行时、动作、验证器和终止原因；系统化
扇出会放大任何泄漏或评分漏洞。

**快速检查点是一项使能原语，而不是回合契约。** 完整系统仍须隔离分支、保护验证器完整性、
限制出口和资源、记录每次分叉与恢复，并保证获胜轨迹可以从其启动根状态复现。

## 第 5 章 — 文件系统分支与运行时检查点

### 保存点的覆盖范围各不相同

三个智能体从同一个仓库基础版本尝试不同修复。把整个目录复制三次当然可行，但会重复依赖，
也会模糊三者之间的关系。写时复制分支可以共享基础版本，只记录私有增量。检查点则能更进
一步，保留运行中的进程。这些机制解决探索与恢复问题，但它们保存的内容不同。

智能体状态可以包含对话、工具事件、文件、进程内存、打开的描述符、浏览器配置档案、挂载卷
和远程资源。文件系统快照至多捕获其文件系统域。感知进程的检查点可以保留内存和进程树。
两者都无法撤销邮件、付款、数据库写入、已发布消息或已泄露凭证。

> *⏪ **恢复规则：** 检查点只能倒回它捕获的状态域；外部影响仍然真实存在。*

![恢复操作止步于外部影响](../assets/diagrams/part-0/05-state-coverage-side-effects.svg)

*图 5.1 — 覆盖更完整的检查点可以改善内部恢复，但发生在捕获域之外的影响仍然存在。*

AgentFS 把文件和智能体历史转化为可查询状态。该项目在 SQLite 中存储文件操作、工具调用
和状态变更，并把快照描述为数据库文件的副本。这提升了可审计性和可移植性。项目也将自身
标记为 beta。数据库后端文件系统不会自动隔离进程、网络或租户；它的关键单元是智能体状态。
[AgentFS 仓库](https://github.com/tursodatabase/agentfs)

BranchFS 把推测性文件系统状态组织成一棵树。它描述了基于 FUSE 的写时复制分支，具有快照
隔离、提交到父节点和中止能力。不同智能体可以通过一个挂载点访问不同分支路径。它的原子
提交表示分支增量相对于父节点作为一次文件系统操作被应用；这并不代表它已经解决了与另一
个持续推进的共享项目之间的任意语义冲突。[BranchFS 仓库](https://github.com/multikernel/branchfs)

DeltaBox 是一个协调文件系统与进程状态以实现检查点和回滚的研究系统。作者报告称，在其
评估设置中，通过组合 OverlayFS 变更和 CRIU 协调的进程状态，实现了毫秒级检查点与恢复。
这些是作者报告的研究结果，并非这里独立复现的数字。架构层面的结论是：**提到“检查点”时，
必须同时说明覆盖范围和一致性边界。**
[DeltaBox 项目页面](https://dongyunpeng-sjtu.github.io/deltabox/)

| 示例 | 单元与部署位置 | 私有状态与生命周期 | 并发与审计 | 返回与不保证事项 |
| --- | --- | --- | --- | --- |
| AgentFS | SQLite 智能体文件系统；两种部署位置模式均可 | 文件、键值状态和工具历史；可复制的快照 | 可查询、可检查的一份可移植历史 | 数据库文件或已挂载文件；不提供进程或租户隔离 |
| BranchFS | 写时复制文件系统分支；两种部署位置模式均可 | 快照视图与私有增量；提交或中止 | 具有显式父子关系的并行分支路径 | 文件系统合并到父节点；无法回滚外部副作用 |
| DeltaBox | 文件系统与进程状态节点；所述设计采用外部控制器 | 协调的文件系统与内存检查点或回滚 | 面向状态对的分支探索 | 恢复后的执行状态；无法撤销远程影响，也没有发布契约 |

三种保存操作回答不同问题。工作空间快照保留源代码和锁定文件；进程检查点还保留运行时状态，
但依赖兼容环境；变更集排除临时状态，捕获相对于具名基础版本的提案。把三者都叫作“状态”
会掩盖各自目的。

覆盖范围和一致性是两个独立问题。一个检查点可能同时包含文件与内存，却在互不兼容的时刻
捕获它们，导致进程中的描述符或缓存与磁盘不一致。协调恢复必须说明哪些状态域共同构成一个
可恢复状态，哪些必须重新构建。

分支操作也需要同样精确：原子提交到父节点不会解决与持续推进基础版本之间的语义冲突。
外部影响即使无法进入检查点，也必须进入历史记录；重试可能需要幂等键、补偿操作或人类决策。

检查点选择的是一段执行历史中的某个位置。**发布则是针对可能已经推进的共享历史执行的另一
种操作。** 恢复一次成功测试运行，不代表其编辑与另一个已接受补丁兼容。文件系统分支提供
私有备选方案；返回边界仍需要捕获、比较、冲突语义和溯源。

## 第 6 章 — 元智能体运行时、控制平面与集群

### 可逆执行轨迹之上的监督者

一个工作智能体即将发出工具调用，却会编辑错误的依赖。元智能体观测到这个拟议动作，在
执行前将其拦截，并分叉出修正分支。如果原分支已经执行，元智能体就回退到前一个事件并
重试。这个简单故事隐藏着三种不同的控制角色。

**元智能体**观测或重定向另一个智能体的决策。**沙箱生命周期控制平面**创建、暂停、恢复、
路由和销毁沙箱环境。**调度器**把这些环境放置到机器上，并管理队列或预热容量。一个产品
可以承担不止一种角色，但这些角色仍然彼此不同。执行命令的沙箱侧守护进程仍是执行工作
进程，不是一种部署位置模式。

> *🧭 **控制规则：** 元智能体监督、沙箱生命周期和集群放置可以协作，但并不是同一种职责。*

![元智能体创建、观测、拦截、回退并分叉工作智能体轨迹](../assets/illustrations/part-0/06-shepherd-meta-agent.png)

*图 6.1 — 元智能体创建并观测工作智能体，拦截拟议动作，然后回退或分叉可逆执行轨迹。
来源：[SHEPHERD 图 1](https://shepherd-agents.ai/)。生命周期控制和集群放置仍是下文所述
的独立角色。*

SHEPHERD 聚焦元智能体语义。该项目描述了类似 Git 的可逆智能体执行轨迹，可以创建、
观测、拦截、分叉、重放和回退。仓库还把软件标记为早期 alpha，API 仍在变化。因此，
应把它理解为研究驱动的轨迹底座，而不是成熟的集群调度器或隔离边界。
[SHEPHERD 仓库](https://github.com/shepherd-agents/shepherd)

Kubernetes Agent Sandbox 聚焦生命周期编排。它为具有稳定身份和持久存储的有状态单实例
工作负载定义 Sandbox 自定义资源，也可以使用预热池。其文档明确说明，底层隔离由 gVisor
或 Kata Containers 等沙箱运行时提供。受管理工作负载可以容纳沙箱内智能体，也可以通过
执行协议服务外部智能体；控制平面不会增加第三种部署位置模式。
[Kubernetes Agent Sandbox 仓库](https://github.com/kubernetes-sigs/agent-sandbox)

SWE-ReX 位于远程执行层。该项目提供跨本地和云端后端、面向智能体的沙箱化代码执行。
在常见用法中，外部智能体运行时获取或连接环境、执行命令并接收证据。它能访问多个后端，
并不因此自动成为调度器。[SWE-ReX 仓库](https://github.com/SWE-agent/swe-rex)

| 角色或示例 | 主要单元与部署位置 | 生命周期权限 | 并发与证据 | 关键不保证项 |
| --- | --- | --- | --- | --- |
| SHEPHERD 元智能体底座 | 可逆轨迹；外部监督者拓扑 | 分叉、重放和回退轨迹执行 | 轨迹历史支持比较与干预 | 早期 alpha 轨迹底座不是调度器或隔离运行时 |
| Kubernetes Agent Sandbox | 有状态沙箱资源；支持两种部署位置模式 | 声明式创建、身份、存储、认领和预热池管理 | Kubernetes 协调和工作负载身份 | 实际隔离机制由其他组件提供 |
| SWE-ReX 远程执行 | 执行环境；外部智能体 | 依后端而定的获取、命令和释放 | 并行远程命令及返回的执行证据 | 远程访问不等于发布或元智能体监督 |

工作节点故障时，调度器停止放置，生命周期控制器把保留状态恢复到替代节点，而运行时报告
这次不连续。结构化事件必须区分工作节点丢失与命令超时，指明恢复边界，并标记结果不确定
的外部影响。租约可以阻止旧工作节点发布过期成果。

替代节点获得新的执行身份，同时保留逻辑会话身份。如果进程状态没有进入检查点，运行时
必须说明最后完成的是哪条命令，以及后续影响是否未知。元智能体随后可以重试、分叉恢复
策略，或停下来接受审查，而不必伪装执行过程从未中断。

预热池可以保留镜像和依赖，却绝不能保留上一个所有者的私有工作空间。认领操作附加会话
身份和策略；释放操作必须清理私有状态。审计事件随后可以区分运行时、协议、工作节点或
工具中的故障。重新分配文件不等于恢复进程，重放历史也无法撤销外部 API 调用；控制平面
必须展示这些边界，而不是用“正在运行”将它们隐藏。

在集群规模下，这些证据会成为控制输入，而不只是调试输出。身份驱动所有权，事件驱动恢复，
资源记录驱动配额和放置。如果没有这些关联，快速复用会把性能优化变成跨会话污染。

## 第 7 章 — 工作空间隔离、变更集与发布

### 返回工作成果也是执行的一部分

智能体现在已经产生三种看似合理的修复。一种升级依赖并增加小型适配器；一种固定旧版传递
依赖；另一种重写受影响模块。它们都通过了各自的私有测试。隔离让每次尝试保持干净，却没有
决定哪个结果属于项目。

> *🚦 **发布规则：** 完成产生私有结果；发布把获准结果变成共享事实。*

不同返回机制承载不同含义。

| 返回形式 | 保留内容 | 冲突行为 | 无法确立的事实 |
| --- | --- | --- | --- |
| 值或 stdout | 一次操作的结果 | 无 | 哪些文件或状态产生了该结果 |
| 文件或制品 | 选定字节 | 通常覆盖或重命名 | 与项目基础版本的关系 |
| 补丁 | 相对于假定基础版本的文件编辑 | 可能失败或只应用一部分 | 完整运行时证据 |
| 分支 | 提交与 Git 谱系 | 合并或变基语义 | 非 Git 状态或策略批准 |
| 变更集 | 捕获的变更，以及明确的基础版本和身份 | 可以比较并解决冲突 | 已被接受进入共享历史 |
| 发布 | 接受后全部应用、否则全部拒绝的状态转换 | 拒绝未解决或被禁止的变更 | 恶意租户隔离 |

假设会话 A 和 B 从 B-10 开始，并编辑同一项设置。B 先发布为 B-11；即使 A 的私有测试
通过，盲目应用 A 也会抹去 B 的策略。变更集让解析器可以比较 B-10、A 和 B-11，然后拒绝、
解决冲突或准备新提案，同时保留 A 的证据。

全量接受或全量拒绝的发布，可以让相互关联的清单、锁定文件、源代码和生成内容作为整体
保留。溯源信息应把每一行获准内容关联到其变更集、会话、起始基础版本、命令、测试、智能体
和决策。它不能证明正确性，却让接受过程可被检查。

健全的工作空间契约会分离四个事件。**完成（Finish）**表示智能体运行时已停止或返回。
**捕获（Capture）**把私有文件系统变更转化为可审查提案。**解析（Resolve）**把该提案与
当前获准的基础版本和策略比较。**发布（Publish）**则使获准结果进入共享历史。任何一步都
可以失败，而不抹去此前证据。

捕获应冻结提案及其基础版本。解析可以读取更新后的共享历史，但在决策时不应修改任何一方。
发布随后把获准变更集连同决策记录原子应用；拒绝则让提案保持私有且可检查。这样的分离能
避免一次重试悄悄改变审查者已经批准的内容。

Container Use 是具体的分支式示例。它的环境组合了专用 Git 分支、容器，以及被追踪的命令
和文件历史。审查者可以检查日志或差异、继续使用环境、合并其分支、把变更应用为暂存修改，
或放弃这次尝试。因此，该产品让返回选择清晰可见，但 Git 仍然是状态与冲突底座。
[Container Use 环境工作流](https://container-use.com/environment-workflow)

### 第一卷案例研究

Ephemeral Sandbox 位于这条返回边界上。该项目描述了多个编码智能体如何在一个共享沙箱内，
基于同一个稳定项目基础版本，在彼此隔离的工作空间会话中工作。每个会话都有私有可写状态。
运行时捕获可审查变更集、根据共享历史解析它，再发布带有溯源信息的获准结果。CLI 与 MCP
界面控制运行时；可观测性围绕状态转换记录活动。
[Ephemeral Sandbox 仓库](https://github.com/Ephemeral-AI-Lab/ephemeral-sandbox)

沿用本技术版图其余部分的分析问题：

- **沙箱单元：** 一个共享沙箱，其中包含多个私有工作空间会话。
- **部署位置：** 它可以通过控制界面服务外部智能体运行时；放置在更大沙箱内部的智能体
  运行时则仍是另一种有效模式。
- **隔离机制：** 面向协作式编码智能体的私有工作空间状态与执行会话边界。
- **私有状态：** 各会话的可写增量、进程，以及发布前捕获的变更。
- **生命周期：** 从显式基础版本创建会话、执行、捕获、发布或拒绝，然后销毁。
- **并发：** 多个会话可以共享不可变的项目事实，而不共享未完成写入。
- **可审计性：** 会话身份、操作、变更集、决策和溯源信息把获准成果与其来源关联起来。
- **返回路径：** 变更集进入一个全量接受或全量拒绝的发布转换。
- **关键不保证项：** 版本 1 的工作空间隔离，不是面向互不信任租户的加固 microVM 边界。

这项限制是核心事实，不是脚注。Ephemeral Sandbox 解决私有并行工作空间和受控发布问题。
需要运行恶意租户代码的部署，仍须采用适当的容器、VM 或 microVM 边界、凭证控制、网络
策略和集群层。发布契约可以与这些系统组合，却不能替代它们。

相邻契约必须继续保持明确。microVM 可以提供隔离，控制器可以替换它，调度器可以放置它，
Ephemeral Sandbox 则可以管理其内部的私有工作空间。稳定身份必须把工作节点、租约、沙箱、
会话、执行、智能体、变更集基础版本和获准版本关联起来。发布仍只有一个职责：决定捕获的
提案是否进入共享历史。

同样的明确边界也能防止能力膨胀。增加 microVM 不会让工作空间发布自动感知冲突。增加溯源
不会阻止内核漏洞利用。增加进程检查点不会撤销泄露的令牌。增加调度器不会把执行工作进程
变成智能体运行时。**有用的架构不是一个标着“智能体沙箱”的巨型方框。** 它是由一组边界
组成的系统；每项保证都可以独立检查，然后组合。
